> 中山大学广州校区南校园「热浪天走哪条路」决策工具。一次离线预计算，前端纯静态查表，零网络、零后端。

## 30 秒看懂

- **这是什么**：中山大学广州校区南校园的热浪天步行决策工具——同一个时刻从 A 到 B，多走几十米换几分钟阴凉，值不值。
- **核心结论**（14:00，老年人活动中心 → 岭南学院）：**多走 44 米，少晒 4.0 分钟**（阴影覆盖 6% → 35%）。

> "现场算"不是另一套近似：`data/graph.js` 把全部路网 + **31 帧 × 613 条边的暴晒千分比（0–1000）**发给浏览器，`js/router.js` 用同一套边权在页面里跑 Dijkstra。冒烟测试对 **2 对起终点 × 31 帧 = 62 个组合**逐个对拍，与 Python 预计算的最大差 **0 米 / ≤0.05 分钟**。

### 1.2 拖时间，结论会变（这是产品的核心，不是彩蛋）

| 时刻 | 太阳高度 | 少晒 | 多走 | 卡片文案 |
|---|---|---|---|---|
| 07:00 | 5.3° | **0.9 分钟** | 110 米 | 多走 110 米，少晒 0.9 分钟。 |
| 10:00 | 40.5° | 3.3 分钟 | 46 米 | 多走 46 米，少晒 3.3 分钟。 |
| **12:00** | **52.1°** | **2.5 分钟（正午时段最低）** | 29 米 | 多走 29 米，少晒 2.5 分钟。 |
| **14:00（默认）** | **43.6°** | **4.0 分钟** | **44 米** | **多走 44 米，少晒 4.0 分钟。** |
| 16:00 | 22.3° | 4.3 分钟 | 43 米 | 多走 43 米，少晒 4.3 分钟。 |
| **16:40** | **14.0°** | **6.2 分钟（全天最高）** | 43 米 | 多走 43 米，少晒 6.2 分钟。 |
| 17:00 | 9.7° | 4.7 分钟 | 43 米 | 多走 43 米，少晒 4.7 分钟。 |

- **不是单调的**：14:00 是 4.0，14:20 跳到 4.8（多走 126 米）；因为"两条路差不多好"时算法会在等价解之间整体切换。
- **正午时段最低、下午最高**：影子长度决定一切。31 帧里"少晒"真正最小的是 07:00 的 0.9 分钟，但那一帧太阳只有 5.3°、属低置信度；10:00–16:00 区间内最低才是 12:00 的 2.5 分钟。
- **低置信度**：太阳 < 15° 的 5 帧（07:00 / 07:20 / 07:40 / **16:40** / 17:00）界面亮黄色横幅；16:40 的 6.2 必须带这一句。
- 校园全部道路阴凉占比（613 条边、**按边长加权**、每条边 4 个采样点；口径见 `docs/DATA-SOURCES.md` §7.4）：07:00 **61.9%** / 09:00 31.7% / **12:00 14.7%** / **14:00 19.9%** / 16:40 42.9% / 17:00 51.3%。

## 2. 怎么跑

```powershell
# 1) 假数据：只验证界面链路（无网络、秒级）
python tools\build.py sample

# 2) 真实数据（三级方案，按顺序试）
python tools\build.py osm        # 主路径：OSM 主 API，一次约 3.6 秒（含校园多边形）
python tools\build.py fetch      # Overpass 优先，任一镜像失败自动降级到 OSM 主 API
python tools\build.py import buildings.json ways.json   # 全都不通时：手动导出的 Overpass JSON
python tools\build.py check      # 只测 Overpass（诊断用，不拉数据）

# 2.5) 底图（道路 / 水系 / 标注）
python tools\build.py basemap    # 从 data/raw/ways.json 离线生成 data/basemap.js，不联网
python tools\build.py lakering --list   # 从路网环路反推候选湖岸（纯几何，不联网）
python tools\build.py lakering --pick 1 --shrink 0.06 --name 园东湖   # 选定后写 data/raw/water.json（approx=true）
python tools\build.py waterblob --x 300 --y 180 --w 240 --h 150       # 或按米坐标放一块椭圆示意水面
python tools\build.py water      # 路名：需要网络（当前 OSM 抓取受阻，路上仍不写字）

# 3) 预计算
python tools\build.py all        # osm/fetch + 阴影 + 路线 + 底图
```

- **底图离线**：`basemap` 纯本地，只读 `data/raw/ways.json`，产出 `data/basemap.js`（32.2 KB：296 段道路 / 1 处示意水面 / 61 条标注）；湖由 `lakering`（路网环路反推）或 `waterblob`（椭圆示意）写入 `data/raw/water.json`，**标记 `approx`**，页面画半透明 + 虚线边；`water` 才联网，主要留作补路名。
- **零依赖**：Python 3.8+ 标准库，不装任何包（没有 shapely / geopandas / numpy / requests / tqdm）。
- **零网络**：`index.html` 双击即用，页面不发任何请求；OSM 数据在构建阶段一次性拉取。
- **Overpass 的坑**：本机网络下 Overpass 的 POST 会被 TLS 中断（`SSL: UNEXPECTED_EOF_WHILE_READING`），所以主路径是 OSM 主 API；`fetch` 会自动降级。
- **校园裁切**：`tools/build.py` 的 `CAMPUS_ONLY = True`，建筑按质心、道路按路段中点过滤；原始 bbox 数据留在 `data/raw/`。

### 3.1 底图与算路的分离

地图上的**道路只是视觉底图，不参与算路**：算路仍走 `data/graph.js` 的 **613 边**图，底图走 `data/basemap.js`；两者都来自同一份 `data/raw/ways.json`（原始 **297 条 way**），一个由 `build.py routes` 生成、一个由 `build.py basemap` 生成，所以不会出现"画的路和算的路不是一回事"。

- **道路**：297 条 way 按可视范围 bbox±60 m 裁切后成 **296 段**，分四档线型 `main` / `local` / `service` / `path`；先描边再铺路面（否则路口会"断"），且必须画在阴影**之前**（否则影子盖不到路上，像路浮在阴影上）。
- **楼名**：285 栋里 68 栋有名字，过滤掉 `572`、`532 533`、`东区3180` 这类 OSM 编号型垃圾名后剩 **60 条**，按"重要度 + 底面积"排序；文字带白色描边，并用矩形碰撞检测自动避让，1400×900 画布上实际画出 **50 个**。
- **湖是示意轮廓，不是测绘数据**：OSM 水系全线抓不到，改由路网环路反推（见 §3.2），`approx: true`，页面画半透明 + 虚线边；**道路名仍然没有**（`data/raw/roadnames.json` 尚未生成：`build.py water` 依赖 OSM 网络，本机受阻未跑通；路上不写字），这条降级依然存在。
- 渲染共 **9 层**（`js/map.js`）：地面 + 100 m 网格 → 水系 → 道路 → 阴影 → 建筑 → 校园边界 → 路线 → 地名标注 → 起终点/比例尺。

### 3.2 湖是怎么来的

OSM 的水系这次**全线拿不到**（本机超时、Overpass 406/502、镜像全挂，wikidata 也没有园东湖条目）。所以湖不是"等数据"，而是**用路网结构反推**出来的：

1. **几何假设**：湖岸一定被园路围一圈，环内不会有建筑。
2. **枚举基本环**：在完整路网（**1194 节点 / 1373 边**，取自 `data/raw/ways.json`，不按通行性裁切）里用生成森林的非树边枚举闭合环，筛**面积 4000–80000 m²、周长 380–1500 m**、环内建筑占比最低的空块。
3. **人工指认**：候选由人在图上确认位置，选定校园东侧中部、中心 **(536, −85) 米**、**面积 16,814 m²（≈1.7 万 m²）**的那块。
4. **内收 + 平滑**：路中线到湖岸本来有一个路宽，多边形向内收 **6%**；再做 **2 轮 Chaikin 切角平滑**（`--smooth 2`，可 0–4，否则岸线顶点太少会像硬邦邦的多边形），最终 **40 个顶点**写入 `data/raw/water.json`，并标记 **`approx: true`**。

页面把 `approx` 水面画成**半透明填充 + 虚线边**，图例写「水系」，湖名以 12.5 px 深蓝色单独标注——**这是示意轮廓，不是测绘数据**，答辩时必须带这一句。命令可复现：`python tools\build.py lakering --list` / `--pick 1 --shrink 0.06 --smooth 2`；快速试位置用 `waterblob --x --y --w --h`。

**仍然缺的**：路名（`data/raw/roadnames.json` 尚未生成），路上不写字——这条降级没有被湖的解决带走。

## 6. 明确不做什么（写下来防跑偏）

- **不做"降温几度"**：那要 Tmrt 模型（长波辐射、风、湿度、衣着），不是这个工具的量级。
- **不做绝对阴影面积承诺**：高度 93% 是 12 m 估算，误差方向双向。
- **不承诺"任何两点都值得绕"**：短距离（如 怀士堂 → 黑石屋 **298 米**）四个时刻两条路几乎一样（少晒 0.0~0.1 分钟）；阴影规划只对**长距离、且有平行道路**的场景有意义——1113 米横穿校园才有 4.0 分钟空间。我们不夸大。
- **不把路线画到校园外**：OSM 官方边界裁切，`CAMPUS_ONLY = True`。
- **不做路线规划 App**：只做"同一时刻两条路线的取舍对比"。
- **不接实时 API**：离线是卖点。
- **不引入框架/依赖**：零 npm、零 CDN。

## 7. 技术要点（面试/答辩可直接用）

1. **研究范围用 OSM 官方校园多边形**（`way 300917756`，1,201,723 m² / 114 顶点），不是矩形 bbox：建筑按**质心**、道路按**路段中点**裁切，保证路线不跨出校门。bbox 内 555 栋 → 校内 **285 栋**（剔除 270 栋）。
2. **太阳位置**：NOAA 简化算法本地计算，1950–2050 内约 0.01°；2026-11-02 12:00 高度 **52.1°**、07:00 **5.3°**。
3. **阴影**：建筑视为竖直棱柱，`L = h / tan(高度角)`（上限 500 m），轮廓 ∪ 平移轮廓取**凸包**（Andrew 单调链）；点在阴影内用**射线法**；一帧阴影环放 **25 m 网格**加速。31 帧 × 285 环 ≈ 861.6 KB。
4. **路线**：校园路网 **613 条无向边 / 474 个节点 / 4 个连通分量 / 143 个独立回路**（`E−V+C`）；Python 侧手写 **heapq Dijkstra**；最快 = 边长，阴凉 = `边长 × (1 + 6.0 × 暴晒比例)`。
5. **任意两点现场算路**：`data/graph.js`（101.2 KB）把全路网（边长毫米精度）+ **31 帧 × 613 条边的暴晒千分比（0–1000）** + **53 个校园地名**发给浏览器；`js/router.js`（约 230 行）用**二叉堆**在页面里跑同一套 Dijkstra，吸附上限 **120 米**，只在**最大连通分量的 466 个节点**上吸附；零依赖、`file://` 可用、不发请求。
6. **换算**：`阴影米数 = 长度 − 暴晒分钟 × 60 × 1.25`（`WALK_SPEED = 1.25 m/s` ⇒ 每分钟 75 米），前端 `CORE.shadeMeters()`；这个换算可一条算式复算（14:00：1113 − 14.0×75 = 63 m ≈ 6%）。
7. **双实现一致性**：冒烟测试对 **2 × 31 = 62 个「起终点 × 帧」组合**逐个对拍 JS 现场算 vs Python 预计算，最大差 **0 米 / ≤0.05 分钟**——所以"现场算"和 PPT 上的数是同一套算法。
8. **低置信度**：太阳 < 15° 的 5 帧亮黄条；< 3° 不画阴影。
9. **测试**：`node tools/smoke.js` **165 条断言**，含 36 条立体视图 + 树断言（投影可逆、只画朝向观察者的面、亮度随太阳方位/高度变化、按钮与指北针同步、切回平面状态干净、深链接；树的确定性/离楼离水离校界/最小间距/图例齐全）、7 条底图断言（`data/basemap.js` 结构完整、道路全部来自本地 OSM 路网、四档线型齐全、道路坐标在可视范围内、楼名标注全部落在校园 bbox 内、标注数 ≥60、按重要度排序）+ **4 条湖断言**（园东湖已画上、湖面积 5000–40000 m²、`approx=true`、湖名以 `k=w` 进标注表）、7 条校园边界回归（含"边界环点数 ≥ 3"）、17 条算路断言（含 4 条地图点选）（同点提示、任意两算、往返对称、5 公里外拒绝、62 组合对拍）与文案精度锁定。
10. **树（520 棵，纯观感，不进阴影）**：`js/trees.js` 用 `mulberry32(SEED=20261103)` 现场撒 520 棵树 —— 沿路每 15 m 一个候选、左右偏 3.6–5.4 m，再在空地里 26 m 网格抖动撒；逐点筛掉"落进楼里、落进水里、离路太近、出校园边界、跟已有树挨太紧"的候选（空间哈希查邻居，全流程 ~50 ms）。**树的坐标不进 `data/*.js`、不进阴影、不进晒度**：`build.py` 的口径一个字没动，所以"阴凉 xx%"这类数字与前一句完全一致。渲染时 1200 m 跨度下真实 4 m 树冠只有 1.8 px，给了一个 3 px 的屏幕最小半径 + 细描边，才读得出是树；立体视图里树冠是"压扁的椭圆"多边形，和楼进同一条深度排序链，近处的树才会盖住远处的楼。
11. **2.5D 立体视图（零依赖）**：`js/iso.js` 在 Canvas 2D 上手算轴测投影——地面绕画布中心旋转 `-26°` 并把纵向压到 `0.80`（斜二测观感），楼按 `h × 3.2` 沿屏幕竖直拔起；每个侧面的亮度 = 外法线·太阳方位（背光压暗偏冷），只画朝向观察者的面，再按轮廓在屏幕上的深度做**画家算法**排序。没有 WebGL、没有 three.js、不读 `.glb`，`file://` 双击照样能跑；点选坐标用同一套投影的**逆变换**反解，旋转后依然点得准；正北角用 `atan2(sin yaw, compress·cos yaw)` 算，指北针才指得对。
