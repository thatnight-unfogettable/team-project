**一句话背景（所有答案共用）**：中山大学广州校区南校园，OSM 官方校园多边形 **1.20 km² / 114 顶点**；校园内 **285 栋建筑（68 栋有名字）**、**613 条道路边 / 474 个节点 / 143 个独立回路**；演示日 **2026-11-02**，07:00–17:00 共 **31 帧**；14:00 主结论 **多走 44 米，少晒 4.0 分钟**（阴影 6% → 35%）。

## Q1：这个项目到底做了多少工作量？一周做得完吗？

- **代码 4781 行**，三块：**前端逻辑 1375**（`app.js` 427 / `core.js` 284 / `map.js` 394 / `router.js` 227 / `proj.js` 43）｜**工具链 2842**（`build.py` 1560 / `smoke.js` 793 / `console-check.js` 246 / `preview.py` 243）｜**页面 564**（`index.html` 122 / `styles.css` 426 / `strings.js` 16）。
- **文档约 1300 行**（README + 6 份 docs + lead 的 `EXAMPLE-QUERIES.md`）。
- 关键不是行数，是**链路完整**：拉数（OSM 主 API）→ 校园裁切 → 高度 → 太阳 → 阴影环 → 路网 Dijkstra → 数据文件 → 前端查表 → 自动测试。
- 实测节奏：**4 天**，其中 1.5 天在改"范围"和"日期"这两个数据决策（返工最多的也是这里）。
- 一句话：**一个人一周内做得完，前提是一开始就把口径定死。**

**如果被追问"为什么不用框架"**：纯静态、零 npm、`file://` 双击可用是**需求**（教室电脑、断网、无管理员权限），不是偷懒。用一个 `<script>` 就能跑的东西，不该拉 200 MB 依赖。

## Q2：创新点在哪？（"这不就是调库"的反驳）

三个层次，从弱到强：

1. **不是调库**：阴影是 `L = h/tan(e)` + 凸包 + 射线法手写的，Dijkstra 是手写 heapq，没有 turf/geopandas/shapely，`tools/build.py` 1560 行零依赖。**可复核**是卖点。
2. **把"阴影"变成"决策数字"**：大多数阴影工具给"哪里有影"，我们给**"多走 44 米换 4.0 分钟不晒"**——这是路线级、时刻级、可比较的量。
3. **方法论上的发现（最硬）**：这次范围从矩形改成校园多边形后，**路网结构彻底变了**——原来只有零散回路，现在 **143 个独立回路**；没有回路，"换一条路"这个产品就不成立。同理，**夏至那天两条路线完全相同（少晒 0.0 分钟）**，是数据告诉我们"这个日期不适合演示"，而不是我们挑好看的日子。

**如果老师说"这不就是最短路径加个权重"**：对，算法是经典的；**创新在数据工程 + 口径设计**：校园边界裁切（否则路线跑出校门）、逐帧预计算、低置信度降级、以及"只承诺相对差异"的诚实边界。

## Q3：和 ShadeMap / SunCalc / 树影地图比，差在哪、好在哪？

| 对比项 | ShadeMap 等 | 本项目 |
|---|---|---|
| 覆盖 | 全球，建筑阴影 | **只做一所校园**，但做到路线级 |
| 输入 | 建筑轮廓（多为 3D 城市模型） | OSM 轮廓 + 楼层数/估算高度 |
| 输出 | 阴影图层 | **两条路线的用时 / 暴晒 / 阴影覆盖 + 文字结论** |
| 时刻 | 连续时间滑块 | **31 帧（20 分钟步长）**，够用且数据小（约 1.08 MB） |
| 树木 | 部分支持 | **不支持**（最大缺口，主动承认） |
| 离线 | 否 | **是**，双击即用 |

**一句话**："它是地图，我们是决策工具；它告诉你哪里有阴凉，我们告诉你**为了阴凉多走 44 米值不值**。"

## Q4：为什么只做校园？换成整个广州还行吗？

**为什么只做校园**：
- 1.20 km² 是**步行决策**的合理尺度（人会为几十米绕路，不会为几公里绕路）。
- 校园内路网是**连通、有回路**的（143 个回路），才可能有"另一条路"。
- OSM 在校园内的数据质量刚好够：建筑轮廓完整、路网密、有官方边界多边形。

**能不能扩到全市**：
- 算法层面：能。`build.py` 只依赖 bbox + 多边形 + 高度，换参数即可。
- 工程层面三个硬约束：①**数据量**（31 帧阴影 = 约 1 MB / 1.2 km²，全市按面积线性放大到几百 MB，必须改成按需算）；②**高度覆盖率**（校外 OSM 更差）；③**API 限额**（OSM 主 API 单次 bbox ≤0.25 平方度，全市要分块 + 限速）。
- 结论：**能扩，但要换架构**（前端实时算 or 服务端切片）。课程作业阶段做校园是最优取舍。

## Q5：OSM 数据合规吗？会不会侵权？

- 许可：**ODbL 1.0**。三条义务：①署名 `© OpenStreetMap contributors`；②公开分发**衍生数据库**需同许可；③只发渲染图（截图/PPT/视频）只需署名。
- 本项目：课程作业**不公开分发数据文件** → 主要义务是署名，已在 README、页面免责说明（`content/strings.js`）、PPT 数据页三处做到。
- 获取方式合规：**OSM 主 API** 单次 bbox 0.00022 平方度（上限 0.25），一次请求、带 User-Agent、不循环爬取。
- 不用百度/高德/Google 的几何数据（条款禁止另行建库）；人工补高度只记录实地能观察到的信息。
- **代码不受 ODbL 传染**：许可证管数据库，不管读取它的程序。

**如果被问"截图里的地图能商用吗"**：截图属于 Produced Work，署名即可；但如果**分发 `data/*.js`**（几何数据），就要按 ODbL 提供。我们课程作业不分发。

## Q6：误差有多大？能不能给个误差棒？

分层回答（这是最能体现工程素养的一题）：

| 误差源 | 量级 | 方向 |
|---|---|---|
| 太阳位置算法 | 约 0.01° | 可忽略 |
| 建筑高度（264 栋估算 12 m） | **主误差源**，可能 ±10 m 以上 | **双向**：高楼低估→偏晒（安全）；低层高估→偏凉（不安全） |
| 4 点采样 | 窄阴影带漏采；正午最快路线只采到 **3%** 阴影 | 偏晒（安全侧） |
| 未计树木/车辆 | 未知，可能很大 | 偏晒（安全侧） |
| 凸包近似（凹形楼） | 楼边十几米内多算阴影 | 偏凉（不安全侧，量级小） |
| 低太阳角（<15°） | 1 m 高度误差 → 3.7~11.4 m 阴影误差 | 误差放大 5 帧 |

**能不能给误差棒**：不能给"绝对阴影面积 ±X m²"，因为高度误差方向不定。**能给的是**：
- 相对差异的稳健性：14:00 两条路线差 44 米、4.0 分钟——这个量级远大于"高度误差造成的路线排序变化"（演示路线两侧建筑已人工核对）。
- 误差放大的解析式：`dL = dh · cot(e)`，任何角度都能现场算（见 `DATA-SOURCES.md` 第 6 节）。

**一句话**："我们不假装有误差棒；我们给出误差公式 + 误差方向 + 哪一段不能信。"

## Q7：为什么坚持纯静态 / 离线？有什么代价？

**收益**：
- 零部署：双击 `index.html` 就能跑，教室电脑、无管理员权限、断网都能用。
- 零网络请求：演示时不会被网速/校园网认证坑。
- 零依赖：没有 npm 供应链风险，五年后还能跑。

**代价**（要主动说）：
- 数据是**快照**：换日期/换城市要重跑 `build.py`（本地运行，约几十秒）。
- 交互受限：不能任意时刻连续插值（只有 31 帧，20 分钟步长）。
- 文件体积：约 1.08 MB 数据 + 代码，`file://` 打开无压力，但不能再大一个数量级。

**结论**：这是**有意识的取舍**——用"数据快照"换"零依赖零网络"。

## Q10：如果重做一次，你会改什么？

按优先级：

1. **先定口径，再写代码**：这次最大的返工是"范围"和"日期"两处，都是数据决策，本可以第一天做完。教训：**演示口径（哪对起终点、哪一天、讲哪个数）应该在写第一行代码前钉死。**
2. **高度别用 12 m 默认值硬扛**：264 栋估算占 93%，应该第一天就把路线两侧 10 栋人工核了（`HEIGHT_OVERRIDES` 机制早就有，只是坦白说没填完）。
3. **先做"回路检查"再定功能**：如果路网没有回路，整个产品不成立。**143 个独立回路**是这次范围的意外收获，也是产品成立的前提——这个检查应该写进第一天。
4. **诚实的边界要写进产品**：低置信度横幅、`content/strings.js` 的免责说明、"只承诺相对差异"——这些不是答辩话术，是产品的一部分。

## Q11：能不能查任意两个地方？只能看你们写死的那两条路吗？

能。两种方式：

- **下拉选**：起点 / 终点各 **53 个校园地名**（怀士堂、黑石屋、岭南学院、伍舜德图书馆、学五饭堂…），OSM 里叫"161""532"这种纯数字的建筑已被过滤掉。
- **地图点两下**：第一下设起点、第二下设终点，自动吸附 **120 米内**的道路节点；超出提示"离校园道路太远"；起终点相同提示"起点和终点是同一个位置，换一个试试"。

算路在**浏览器里**跑（`js/router.js`，227 行，手写二叉堆 + Dijkstra），**完全不联网**，卡片右上角标「现场计算」并显示「全长 xx 米」。只有主路网（最大连通分量 **466 个节点**）允许吸附——孤岛小路吸上去会算出"没有路"。

## Q12：现场算的数，会不会和你们 PPT 上的不一样？

不会，而且是**同一套算法**，不是另一套近似：

- `data/graph.js`（**101.2 KB**）把 **474 节点 / 613 边**（边长毫米精度）+ **31 帧 × 613 条的暴晒千分比（0–1000）**发给浏览器；
- 冒烟测试把 **2 对起终点 × 31 帧 = 62 个组合**逐个对拍 JS 现场算 vs Python 预计算：**长度必须全等（实测最大差 0 米）**、暴晒分钟差 **≤0.05 分钟**；
- 所以现场报两个地名，数会和 PPT、和 `data/routes.js` 一致（14:00 默认那组仍是 1113 米 / 44 米 / 4.0 分钟）。

## Q13：既然都能现场算，为什么还要预计算？

**因为两类计算的性质不同，边界分开：**

- **阴影是几何确定量**：给定楼高、轮廓、太阳位置，结果唯一——适合**离线算一次**（31 帧 × 285 栋），否则浏览器里跑凸包 + 射线法会很慢；
- **路径选择随起终点变**：用户可能问任意两点，**不能预计算所有组合**（474² 量级），所以现场跑 Dijkstra 最划算；
- 两者共用同一份边权数据，所以结果一致。

这也是能纯静态的原因：**几何预计算 + 少量路由现场算 + 全本地文件**，没有一处需要服务器。

## Q14：你们这个真的有用吗？短距离是不是就没差别？

**对，短距离常常没差别，我们不夸大。**

- 短距离例子：怀士堂 → 黑石屋只有 **298 米**，四个时刻两条路线几乎相同（**少晒 0.0~0.1 分钟**）；
- 长距离才有空间：横穿校园的 1113 米（老年人活动中心 → 岭南学院）在 14:00 有 **4.0 分钟**的取舍空间；
- 结论：**阴影规划只对"长距离 + 有平行道路"的场景有意义**——这个工具解决的是"值不值得为阴凉绕路"，不是"任何两点都能优化"。

## Q15：这些楼名和道路是哪来的？是不是手画的？

不是手画的，全部是真实 OSM 数据：

- **道路**：`data/raw/ways.json` 里原始 **297 条 way**，按可视范围 bbox±60 m 裁切后成 **296 段**（297 是 way 数、296 是底图段数，两个口径别混），分 `main`（主干道 / trunk / primary / secondary / tertiary）、`local`（校内路 residential / unclassified）、`service`（服务道）、`path`（步道 footway / path / pedestrian / steps）四档线型；
- **楼名**：285 栋里 **68 栋有名字**，过滤掉 `572`、`532 533`、`东区3180` 这类 OSM 编号型垃圾名后剩 **60 条**，按"重要度 + 底面积"排序；页面做矩形碰撞避让，1400×900 下实际画出 **50 个**（画不下的直接跳过，宁可少画也不压字）；
- **同源**：底图 `data/basemap.js`（31.5 KB）和算路 `data/graph.js`（613 边）都从同一份 `ways.json` 派生——`build.py basemap` 画图、`build.py routes` 算路，所以"画的路"和"算的路"不会打架；
- 数据仍是 ODbL 1.0，页面免责说明里有署名。

**一句话**："底图不是画的，是 OSM 数据离线渲染的；和算路同一份数据源，不是两张皮。"

## Q16：为什么地图上没有湖 / 路上没有路名？

**这是有意的降级，不是 bug。**

- 湖（`natural=water`）和道路 `name` 不在已有缓存里，必须现场联网补抓；本次 OSM 抓取**全线不通**（本机直连超时、代理 502，Overpass 4 个镜像 + 法国站 + OSM 主 API 全部失败），所以**当前版本不绘制水系、路上不写字**；
- 已备好补救命令：`python tools\build.py water` —— 网络一通就跑，会把 `natural=water` 存成 `data/raw/water.json`、把 `highway` 的 `name` 存成 `data/raw/roadnames.json`，再跑一次 `python tools\build.py basemap` 就会出现在页面上；
- 宁可缺，不编造：我们不会用示意图形冒充真实湖岸线。

**答辩口径**："水系和路名属于底图增强，数据没抓到就不画；命令已经写好，网络恢复后两条命令就能补上。当前页面能保证的是：看到的路和楼名 100% 是 OSM 真数据。"

## 附录 A · 老师连问三串（真实课堂节奏）

**第一串（数据）**：数据哪来的 → OSM → 合规吗 → ODbL 署名 → 建筑高度哪来的 → 21 栋楼层数 + 264 栋 12 m 估算 → 准吗 → 双向误差，只承诺相对差异。

**第二串（方法）**：阴影怎么算 → `L = h/tan(e)` + 凸包 → 怎么判断点在阴影里 → 射线法 → 路线怎么选 → Dijkstra + `COOL_FACTOR` 权重 → 为什么 6 → 手调演示档位，不是标定值。

**第三串（产品）**：为什么做这个 → 每天中午真的要走这条路 → 为什么不用 ShadeMap → 它给地图我们给决策 → 降温几度 → 不承诺，那是 Tmrt 模型 → 树算了吗 → 没算，最大缺口。
