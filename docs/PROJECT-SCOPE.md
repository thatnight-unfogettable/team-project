# 项目范围定义（PROJECT-SCOPE）

> **用途**：本项目"做什么、为谁做、做到什么算完"的唯一真相源；改需求先改这里，不要口头改。
> **权威分工**：协作与流程看仓库根 `AGENTS.md`；数字与口径看 `docs/AGENTS-10.md`；范围与需求看本文档。三者冲突时必须当次修掉。
> **基线**：2026-11-03，交付物已跑通（`node tools/smoke.js` 212 条断言全过）。本文档按仓库现状回填，不是事前规划稿。

---

## 1. 一句话目标

**用"建筑阴影 + 31 帧时变预计算"的纯静态离线工具，帮中山大学广州校区南校园的步行者在 11:00–16:00 高温时段从 A 走到 B 时回答一个问题：多走几十米换几分钟阴凉，值不值。**

（更短一句：把"凭感觉挑一条路"换成"多走 44 米 vs 少晒 4.0 分钟"的可比较数字。）

---

## 2. 目标用户与场景

| 问题 | 回答 |
|---|---|
| 用户是谁？ | **校园内步行者**：学生为主（午间往返宿舍/食堂/教学楼），其次是教工，以及去老年人活动中心/家属区的探访者。共同点：没有车、午间要横穿校园、对"晒多久"敏感。 |
| 他们在什么情况下会用？ | **11:00–16:00 的一次性长距离出行**（≥500 m）：下课回宿舍、去食堂、去图书馆、陪长辈去活动中心。**短距离（<300 m）不是目标场景**——两条路几乎没差别，我们不夸大。 |
| 现在他们怎么解决？ | 用高德/百度挑"最快"，或凭记忆走"感觉有树荫"的那条；没有任何工具帮他们比较"绕路换阴凉"的性价比，也没有工具告诉他们"这个时刻绕路是否值得"。 |
| 我们的方案好在哪？ | 只回答一个**可比较、可复现**的问题：**多走 44 米，少晒 4.0 分钟**；拖时间轴会看到取舍随时段变化；不可信的帧（太阳 <15°）主动标黄降级，不拿低置信度数当卖点。 |
| 具体 persona（开场 25 秒用） | 午间 14:00，一位要去老年人活动中心接长辈回岭南学院的学生/教工，手机可能没流量、不想装 App；这位步行者打开本地页面（双击 `index.html`），拖到 14:00，看到"最快 14.8 分钟里有 14 分钟在太阳下"，而另一条路**多走 44 米、少晒 4.0 分钟**。 |
| 为什么默认起终点是这一对？ | **老年人活动中心 ↔ 岭南学院 1113 米**，是校内最典型的"长距离 + 有平行道路"组合（两条路只差 44 米），也是校内长者、教工的真实动线——**不是为演示好看挑的**。第二组「学生饭堂 → 老年人活动中心」（1320/1377 米，多走 57 米、少晒 3.3 分钟）用于证明结论不是单点巧合。 |

## 3. 核心功能（P0 五条，按优先级排）

> P0 = 没有它项目就不成立；P1 = 有更好；P2 = 有余力再做。每条验收标准都必须能用一条命令或一次操作判定。

| 优先级 | 功能 | 一句话说明 | 验收标准（怎么算做完） |
|---|---|---|---|
| **P0** | 两条示范路线对比 | 默认 14:00「老年人活动中心 → 岭南学院」；「路线对比」标题右侧的「示例 A / 示例 B」按钮切换两组预计算示例 | 页面卡片逐字显示「多走 44 米，少晒 4.0 分钟。」；`data/routes.js` 14:00 pair0 = 14.8 / 14.0 / 1113 与 15.4 / 10.0 / 1157；点「示例 B」后显示「多走 57 米，少晒 3.3 分钟。」且 `#route-tag` = 「预计算」；`node tools/smoke.js` 的 14:00 数值断言通过 |
| **P0** | 31 帧时变阴影 | 07:00–17:00 每 20 分钟一帧，拖时间滑块时阴影、卡片同步重算 | 滑块 0–30 共 **31 档**、首帧 07:00 / 末帧 17:00；每帧 285 个阴影环；太阳 <15° 的 **5 帧**（07:00/07:20/07:40/16:40/17:00）出现黄色低置信度横幅；smoke 数据契约断言通过 |
| **P0** | 任意两点现场算路 | 53 个校园地名下拉，或地图上点两下（第一下起点、第二下终点，吸附 120 m 内道路节点）；浏览器现场跑 Dijkstra，不发请求 | 选任意两个不同地名能出双路线；`#route-tag` = 「现场计算」并显示「全长 xx 米」；与 Python 预计算在 **62 组「帧 × 起终点」**上长度差 **0 米**、暴晒差 **≤0.05 分钟**；起终点相同给出提示、5 km 外拒绝；smoke 17 条算路断言通过 |
| **P0** | 纯静态、离线、零依赖 | 双击 `index.html` 即用；无 npm / 无框架 / 无构建工具 / 无 CDN / 运行时零网络 | `file://` 打开无控制台错误；DevTools Network 面板 **0 请求**；`js/*.js` 与 `index.html` 中 `fetch(` / `XMLHttpRequest` / `sendBeacon` / `import(` 均 0 命中；`index.html` 无 `type="module"` |
| **P0** | 数据底图与合规 | 296 段道路（四档线型）+ 1 处示意水面（园东湖，`approx`）+ 61 条标注；页脚保留 OSM 署名 | `data/basemap.js` 7 条底图断言 + 4 条湖断言全过；页脚含「© OpenStreetMap contributors」与「示意轮廓 / 非测绘数据」；`LICENSE` 说明代码/文档保留所有权利 + 数据 ODbL |
| P1 | 低置信度主动降级 | 太阳低于 15° 时亮黄条并写「此时数据仅作参考」；低于 3° 不画阴影 | 第 2 条 P0 已覆盖主验收；额外要求低置信度帧固定为 5 个，不多不少 |
| P2 | 路名 / 树冠阴影 | 路上写字、把树冠纳入遮挡体（已知缺口） | 当前 **未做**：`data/raw/roadnames.json` 尚未生成；树冠需 DSM/LiDAR，只作未来工作 |

## 4. 明确不做（范围外）

> 写下来防止后期无休止加需求。有人提新需求 → 先问"放到 P2 还是砍掉"。

- **不做校园外 / 多校区**：只覆盖 OSM 官方南校园多边形 **1.20 km²**（`CAMPUS_ONLY = True`，建筑按质心、道路按路段中点裁切）；扩到第二个校区要换边界 + 高度 + 重跑管线，不是改个配置。
- **不做实时天气 / 实时温度**：演示日固定为历史日 **2026-11-02** 的太阳位置；不接气象 API、不判断"今天热不热"，也不做高温预警。
- **不做"降温几度" / 体感温度**：那需要 Tmrt 模型（长波辐射、风、湿度、衣着、代谢）；本项目只输出物理定义明确的"暴晒分钟数 / 阴影覆盖米数"，**不输出 UTCI 或体感温度**。
- **不做绝对阴影面积承诺**：高度 **92.6% 是 12 m 估算**（264/285 栋），误差方向双向；只承诺**同一时刻两条路线的相对差异**。
- **不做树冠、车辆、临时棚、地形起伏的遮挡**：这是已知**最大缺口**，真实阴影只会比图上多（结论偏"晒"，安全侧）；树冠很可能是校园阴凉主力。
- **不做导航 App / 实时路径规划服务**：无后端、无账号、无地图瓦片、无转向级导航；只做"同一时刻两条路线的取舍对比"。
- **不做非步行方式**：不覆盖骑行、驾车、公交，速度常量固定 `WALK_SPEED = 1.25 m/s`。
- **不接商业地图几何 / 瓦片 / 在线路径规划 API**（高德、百度、Google）：条款禁止把数据用于另建数据库；几何数据只用 OSM（ODbL 1.0）。
- **不做水系的精确岸线**：园东湖由路网环路反推 + 人工指认（中心 (536, −85) 米、约 16,814 m²），标 `approx: true`，**不是测绘数据**。
- **不做直射/散射分离、半影、大气折射修正**：太阳位置用 NOAA 简化算法（误差约 0.01°），低角度误差用"低置信度"提示兜住。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 建筑高度 **92.6% 是 12 m 估算**（264/285 栋，`height` 标签 0 个） | 阴影长度与高度成正比，误差方向双向 | 只承诺**相对差异**；优先补演示路线两侧 10 栋（`HEIGHT_OVERRIDES`）；讲稿主动说"93% 是估算" |
| **树冠未计入** | 真实阴影比图上多，校园林荫道可能是阴凉主力 | 主动写进边界（README §6、PITCH Q3/Q10）；技术路线 DSM / LiDAR 已留口 |
| **园东湖是示意轮廓** | 岸线与真实湖岸有偏差 | 数据标 `approx: true`、页面虚线边 + 半透明；对外材料必带"非测绘数据" |
| **单日 + 单校区**（2026-11-02 / 南校园） | 结论不能外推到其他日期或校园 | 明确声明是"演示日 + 单一校区"；换日期/校区需重跑 `shadows` + `routes` + `basemap` |
| **`COOL_FACTOR = 6.0` 是手调演示档位** | 绕路偏好没有用户依据 | 文档明确写"演示档位，不是标定值"；下一步用用户调研/热暴露调查定 |
| **低太阳高度角**（<15°） | 1 m 高度误差被放大到 4~11 m | 5 帧亮黄条主动降级；<3° 不画阴影；16:40 的 6.2 分钟必须带"该帧 14°、低置信度" |
| **OSM 网络受阻**（Overpass TLS 断、水系/路名抓不到） | 路名缺失、水系需反推 | 三级拉取（`osm` 主 API → `fetch` → `import` 离线兜底）；路名标注为**有意降级**；湖用 `lakering` 反推 |
| **双实现漂移**（JS 现场算 vs Python 预计算） | 演示数字与现场数字不一致 | smoke 对 **62 个组合**对拍：长度差 0 米、暴晒差 ≤0.05 分钟，作为硬门禁 |

> 实际是**单人 + AI agent**（不是 4 人团队；旧模板的 4 人分工与 hub relay 已作废）。
