## 0. 一页结论（先看这个）

| 环节 | 依据 | 可信程度 | 主要误差来源 |
|---|---|---|---|
| 研究范围 | OSM 官方校园多边形 `way 300917756`「中山大学(广州校区南校园)」，1,201,723 m²、114 个顶点 | 高（官方校园边界） | 边界与校园实际围墙可能有出入 |
| 建筑轮廓、路网 | OpenStreetMap（ODbL 1.0），经 OSM 主 API 拉取，再按校园多边形裁切 | 高（人工测绘，有几何噪声） | 轮廓简化、缺漏 |
| 地图底图（道路 / 楼名 / 湖） | 同一份 `ways.json` + 建筑名离线渲染成 `data/basemap.js`：**296 段道路**（四档线型）/ **60 条楼名** + **1 条湖名**；湖是路网环路反推的**示意轮廓**（`approx`，16,814 m²） | 道路/楼名 高（与算路同源）；湖 **示意** | 湖非测绘数据；**缺路名**（OSM 抓取受阻） |
| 太阳位置 | NOAA / 天文年历简化算法（本地计算） | 高（1950–2050 内约 0.01°） | 未计大气折射、半影 |
| 建筑高度 | 21 栋有 `building:levels`（×3.2 m）；264 栋估算 12 m；人工覆盖可选 | **中低**（本项目最大的不确定性） | 估算栋偏差，**方向双向**（见 4.2） |
| 阴影 | 棱柱阴影几何 `L = h / tan(高度角)`，取凸包包络 | 中高（高度可靠时） | 高度误差 + 低角度放大 |
| 暴晒分钟数 / 阴影覆盖米数 | 每条边 **4 个采样点**求暴晒比例，按 1.25 m/s 换算 | 中（会漏采窄阴影带） | 采样粒度、帧粒度 |
| 树木、车辆、临时棚 | **未计入** | — | 单方向缺失，结果偏"晒"（保守） |

**一句话口径**：阴影是"只看建筑"的保守估计，暴晒时间是**上界**；我们**只承诺同一时刻两条路线的相对差异**，不承诺绝对阴影面积。
**当前本事**：校园 1.20 km²（OSM 官方边界）、285 栋建筑、613 条道路边、31 帧时变阴影；最拿得出手的是"同一时刻两条路线差多少阴影"。

### 1.1 为什么要按校园多边形裁切（这是本项目最关键的一次纠错）

上一版直接用一个矩形 bbox，看起来"范围够大"，其实混进了大量校外街区：布匹市场（广州国际轻纺城）、商场、周边住宅。**更致命的是两条演示路线的终点落在校园外**，路线实际上是往东跑出校门的。

现在的做法（`tools/build.py` 的 `CAMPUS_ONLY = True`）：

- 建筑：**质心**在多边形内才保留；
- 道路：**路段中点**在多边形内才保留（保证路线不会穿出校门）；
- 原始 bbox 数据仍存在 `data/raw/buildings.json`（**555 栋**）供回溯，但 `data/buildings.js` 只有校内的 **285 栋**。

| 指标 | 数值 | 说明 |
|---|---|---|
| bbox 内原始建筑 | **555 栋** | `data/raw/buildings.json` |
| 校园内保留 | **285 栋**（其中 **68 栋有名字**） | `data/buildings.js` |
| 校外界外剔除 | **270 栋** | 555 − 285 = 270 |
| 道路 | 297 条 way → 剔除 **760 段**校外路段 → **474 个节点 / 613 条边** | `_build_graph()` 输出 |
| 连通分量 | **4 个**；最大分量 **466 节点 / 607 边** | 同上 |
| 独立回路（`E - V + C`） | **143 个**（最大分量内 **142 个**） | `613 - 474 + 4 = 143` |
| 阴影环 | 31 帧 × **285 个环**（每栋楼一个） | `data/shadows.js` |

**方法论一句话**：没有回路就没有"换一条路"。**143 个独立回路**是这个产品能成立的前提；如果路网是一棵树，任何"多走换阴凉"都是空话。

> 数字自洽说明：`E - V + C = 613 - 474 + 4 = 143`；最大分量内 `607 - 466 + 1 = 142`。答辩时说"校园内 143 个独立回路"即可。

## 2. OSM 数据的获取与合规

### 2.1 许可：ODbL 1.0（三条义务）

OpenStreetMap 的数据（建筑轮廓、道路、`height` / `building:levels` 标签、校园多边形）以 **ODbL 1.0（Open Database License）** 发布：

1. **署名**：标注 `© OpenStreetMap contributors` 并给出许可说明链接。
   - 标准写法：`地图数据 © OpenStreetMap contributors，依 ODbL 1.0 许可使用`
   - 官方版权页：<https://www.openstreetmap.org/copyright>
   - ODbL 全文：<https://opendatacommons.org/licenses/odbl/1-0/>
2. **相同方式共享**：**公开分发**基于 OSM 数据产生的**衍生数据库**（本项目里是 `data/buildings.js`、`data/shadows.js` 这类几何数据）时，衍生库需要同样以 ODbL 提供。
3. **产出物（Produced Work）**：只发布渲染出来的图（截图、PPT 地图页、演示视频）时，只需署名，不触发数据库的相同方式共享。

**本项目的实际判断**：课程作业不公开分发数据文件 → 主要义务是**署名**。做法：README、页面免责说明（`content/strings.js`）、PPT 数据页三处都署名。
**代码不受 ODbL 传染**：ODbL 管数据库，不管读取它的程序。

### 2.2 获取方式：为什么主用 OSM 主 API，而不是 Overpass

实测结论：**在本项目的网络环境下，Overpass 的 POST 会被 TLS 中断**（`SSL: UNEXPECTED_EOF_WHILE_READING`），改成 GET 后也不稳定。因此现在的命令行是三级方案：

| 命令 | 做什么 | 什么时候用 | 实测 |
|---|---|---|---|
| `python tools/build.py osm` | 直接 GET `https://api.openstreetmap.org/api/0.6/map?bbox=...`，一次拿到 bbox 内建筑 + 路网 + 校园多边形（OSM XML） | **主路径** | 约 3.6 秒 |
| `python tools/build.py fetch` | Overpass 优先，任一镜像失败**自动降级**到 OSM 主 API | 网络正常、想走 Overpass 时 | 视网络 |
| `python tools/build.py import buildings.json ways.json` | 用浏览器/overpass-turbo 手动导出的 Overpass JSON 落盘 | 全都不通时的**离线兜底**（已实现并测过） | 秒级 |
| `python tools/build.py check` | **只测 Overpass** 连通性，用于诊断"是 Overpass 挂了还是网挂了" | 排障 | — |
| `python tools/build.py basemap` | 从本地 `data/raw/ways.json` + `data/raw/water.json` 生成底图 `data/basemap.js`（296 段道路 / 1 处示意水面 / 61 条标注） | 任何时候，**纯离线、不联网** | 秒级 |
| `python tools/build.py lakering --list` | 在完整路网（1194 节点 / 1373 边）里枚举闭合环，列出"像湖"的候选空块（面积 4000–80000 m²、周长 380–1500 m） | 需要湖但没有 OSM 水系时，**纯离线** | 秒级 |
| `python tools/build.py lakering --pick 1 --shrink 0.06 --smooth 2 --name 园东湖` | 取第 N 个候选，向内收 6%、2 轮 Chaikin 平滑，写 `data/raw/water.json`（`approx: true`） | 候选指认后 | 秒级 |
| `python tools/build.py waterblob --x 300 --y 180 --w 240 --h 150` | 按米坐标放一块椭圆示意水面（48 顶点），写 `data/raw/water.json`（`approx: true`） | 快速试位置/大小 | 秒级 |
| `python tools/build.py water` | 联网补抓 `natural=water` → `data/raw/water.json`、道路 `name` → `data/raw/roadnames.json`；抓完再跑一次 `basemap` 才上图 | 网络可用时（湖已有示意版，此命令主要补**路名**） | **当前不可用**（OSM 抓取受阻） |

**主 API 的合规性**：`/api/0.6/map` 对单次请求的 bbox 面积有上限（**0.25 平方度**），本项目 bbox 约 **0.00022 平方度**（0.0127° × 0.0176°），远低于上限；一次请求、带 User-Agent、不循环拉取，符合 OSM 使用政策。

> 演示话术（被问到就照读）："数据是提前一次性拉下来、离线算好的；页面本身不发任何网络请求。Overpass 在我们网络下会被 TLS 掐，所以主用 OSM 主站 API，一次请求 3.6 秒。"

### 2.3 明确不用什么

- **不使用**百度/高德/Google 地图的几何数据或瓦片：其服务条款禁止把数据用于另行构建数据库。
- 人工补录高度时，**只记录肉眼/实地能观察到的信息**（几层楼、是不是大空间），不抄录商业地图的数值。
- 不使用任何在线地理编码/路径规划 API（离线是卖点，也是合规上的省事）。

## 3. 太阳位置算法与"为什么换演示日期"

### 3.1 出处与公式链

`tools/build.py` 的 `solar_position()` 用的是**低精度太阳坐标**的标准做法（与 NOAA Solar Calculator、天文年历简化公式同源）：

```
UTC 时刻 → 儒略日 JD → 平黄经 L、平近点角 g → 黄经 λ → 黄赤交角 ε
        → 赤经 RA、赤纬 dec → 格林尼治恒星时 GMST → 地方恒星时 LST
        → 时角 H → 高度角 el、方位角 az
```

- 时区固定 `TZ_OFFSET_HOURS = 8`（中国无夏令时）。
- 方位角以**正北为 0°、顺时针增加**（东 90°、南 180°、西 270°）。
- 2026-11-02 实测输出（`data/meta.js`，与本表逐条一致）：07:00 **5.3°** → 10:00 **40.5°** → 12:00 **52.1°** → 14:00 **43.6°** → 16:40 **14.0°** → 17:00 **9.7°**。

参考：NOAA Global Monitoring Laboratory Solar Calculator（<https://gml.noaa.gov/grad/solcalc/>）及《天文年历》低精度太阳位置公式。

### 3.2 精度与未计入项

| 项 | 量级（约） | 对本项目的影响 |
|---|---|---|
| 低精度太阳位置公式误差（1950–2050） | 约 0.01° | 阴影长度相对误差约 0.1%，可忽略 |
| 大气折射 | 地平线约 0.57°；高度角 10° 时约 0.09°；30° 时约 0.03° | 低角度时真实太阳更高 → 真实阴影**略短于**我们算的 |
| 太阳视半径（半影） | 约 0.27° | 按点光源算，阴影边缘是硬边；真实边缘有约 `L·tan(0.27°)` 的模糊带 |
| 地形起伏、屋顶细节、阳台出挑 | 未建模 | 局部阴影形状误差 |

### 3.3 时间帧与低置信度区间

- 帧范围 07:00–17:00（11 月广州日出约 06:35、日落约 17:50，再往后太阳已在地平线下，算阴影没有意义）。
- 太阳高度角 < 15° 的帧：**07:00（5.3°）、07:20（9.6°）、07:40（13.9°）、16:40（14.0°）、17:00（9.7°）**——这 5 帧界面显示黄色"低置信度"横幅。
- 这不是 bug，是设计：低角度时 1 m 的高度误差会被放大到 4~11 m（见第 6 节），此时"精确到米"没有意义。

### 3.4 为什么从夏至换到 11 月 2 日（**这是加分点**）

最初选夏至（6-21）是为了"阴影最长、视觉冲击最大"，用同一套管线在**同一份 285 栋校园数据**上重跑后发现这个选择让**产品说不通**：

| 日期（12:00 帧） | 太阳高度 | 19 m 高楼的影子 | 校园道路阴凉占比（613 条边实测） | 两条演示路线 |
|---|---|---|---|---|
| 2026-06-21（夏至，放弃） | **83.4°** | `19 / tan83.4° ≈ 2.2 m`（约楼高的 0.12 倍） | **1.0%** | **完全相同：少晒 0.0 分钟、多走 0 米**（两条都是 14.8 分钟、暴晒 14.8 分钟、0% 阴影） |
| 2026-11-02（演示日） | **52.1°** | `19 / tan52.1° ≈ 14.8 m`（约楼高的 0.78 倍） | **14.7%** | 少晒 **2.5 分钟**、多走 **29 米**（阴影覆盖 3% → 22%） |

- **正午道路阴凉占比 1.0% vs 14.7%，差 14.7 倍。**
- 夏至那天 10:00 只少晒 1.6 分钟（多走 2 米）、14:00 只少晒 0.6 分钟（多走 13 米）——**两条路线几乎一模一样**，这个产品在夏至没有内容可讲。
- 同一栋楼，11 月正午的影子是夏至正午的 **6.4 倍**（`cot52.1° / cot83.4°`）。

> 答辩口径："夏至正午 83.4°，楼影只有楼高的 0.12 倍，校园道路阴凉占比 1.0%，两条路线完全相同；11 月初正午 52.1°，影子 0.78 倍，阴凉占比 14.7%，差异才出现。所以演示日是我用数据选的，不是随手定的。"
> 补充一句更硬的：夏至 12:00 那帧**连"最快"和"阴凉"都重合**（少晒 0.0 分钟、多走 0 米）——不是算法坏了，是几何上真的没有阴凉可选。

> **两个"覆盖率"别混用**：`1.0% / 14.7%` 是**校园所有道路**在 12:00 的平均阴凉占比（用来论证"这一天有没有差异"）；`6% → 35%` 是**某一条具体路线**在 14:00 的覆盖率（用来讲产品）。两者口径不同，被追问时先说清是哪一层，别互相印证。

## 4. 建筑高度：来源、覆盖率和误差方向

高度是**整个项目最大的误差源**，因为阴影长度与高度成正比（`L = h / tan(el)`，见第 6 节）。

### 4.1 覆盖率：校园里几乎没有楼层数（要主动说）

| 来源 | 代码里的 `src` | 做法 | 当前栋数 | 典型误差（约） |
|---|---|---|---|---|
| ① OSM 高度标注 `height` | `osm` | 直接读 `height` / `building:height` | **0 栋**（校园数据里一条都没有） | ±1~2 m |
| ② 楼层数换算 | `osm_levels` | `building:levels × 3.2 m` | **21 栋（7%）** | 5 层楼约 ±2 m（±12%） |
| ③ 人工覆盖 | 覆盖后仍显示原 `src` | `tools/build.py` 的 `HEIGHT_OVERRIDES = {way_id: 高度}`（已实现） | 按演示路线逐栋补 | 约 ±1 层 ≈ ±3~4 m |
| ④ 兜底估算 | `estimated` | 标签全缺时给默认 **12.0 m** | **264 栋（93%）** | 可能 ±10 m 以上 |

**覆盖率必须说实话**：285 栋里只有 **21 栋（7%）** 有 `building:levels`，**一栋 `height` 标签都没有**。旧版那个"大部分楼都有真实楼层数"的好看数字来自校外商住区，按校园裁切后原形毕露——现在只能如实说 21/285。

### 4.2 误差方向：**双向**，不要再说"偏保守"（上一版的错）

- 默认 12 m 对**高楼**（图书馆、教学楼）是**低估** → 阴影算短 → 暴晒算多 → 偏"晒"（安全侧）。
- 默认 12 m 对**一两层的老建筑**（老宿舍、小卖部、门房）是**高估** → 阴影算长 → 暴晒算少 → **偏"凉"（不安全侧）**。
- 两个方向同时存在，**净方向不确定**。因此：
  > "我们不承诺绝对阴影面积，只承诺同一时刻两条路线的相对差异。"
- 演示路线两侧的建筑是人工核过的（`HEIGHT_OVERRIDES`），这是"相对差异"能站住的前提。

**为什么层高选 3.2 m**：3.0 m 是净层高，阴影算的是**屋顶高度**，要含楼板与女儿墙。3.2 m 是偏高假设。

### 4.3 待补清单：`data/height-report.csv`（60 行，6 列）

列：`id, name, 当前高度(估算), 距演示起终点(米), 底面积(平方米), 人工高度(填这里)`；排序：离两条路线起终点近 → 有名字 → 底面积大；最多列 `HEIGHT_REPORT_LIMIT = 60` 栋。**第一行是「伍舜德图书馆」**（id 300957338，估算 12.0 m，距起终点 105 m，底面积 1590 m²）。

## 5. 保守性说明：没算树、没算车、没算临时棚

### 5.1 方向性论证（对"漏算"而言）

对任意地面点，真实是否被遮挡 = 建筑 ∪ 树木 ∪ 车辆 ∪ 构筑物 ∪ 地形 的并集。我们只算了"建筑"一项：

```
计算阴影 ⊆ 真实阴影        （唯一例外：凹形建筑轮廓附近的局部外扩，见 6.1）
⇒ 计算出的"暴晒时间" ≥ 真实暴晒时间
⇒ 暴晒分钟数是上界（偏晒）
⇒ 推荐的"阴凉路线"在现实中只会比图上更阴凉
```

**这个方向很重要**：宁可告诉用户"这条路晒 14 分钟"，也不要因为漏算而说"很凉快"、结果他走过去被晒。决策工具的错误要往**安全侧**倒。

### 5.2 但有两个反方向的风险，必须承认

1. **高度默认 12 m 的方向是双向的**（见 4.2）：对低层老建筑会高估高度 → 阴影偏长 → 偏"凉"，这是**不安全侧**。所以高度核对优先于其它优化。
2. **太阳高度角 < 15°** 时绝对阴影长度不可信（第 6 节），此时"偏晒"结论也可能翻转。

### 5.3 校园里树荫是主力，这是已知的最大缺口

11 月 2 日正午校园道路阴凉占比 **14.7%**、14:00 是 **19.8%**——这个数字低得反常，原因很可能是**建筑的阴影本来就有限，而树冠没有进模型**。广州校园的林荫道，树冠遮挡的体感权重很可能高于建筑（这是判断，没有实测，所以不给数字）。

- 单棵 8 m 高的树，在高度角 10° 时投出 `8 × 5.67 ≈ 45 m` 的影子——足以覆盖整条人行道。
- 下一步技术路线：OSM 的 `natural=tree` / `landuse=forest` 有树位但**没有树高、冠幅、疏密**；真正能用的是 DSM（数字表面模型）或 LiDAR 点云。我们的投影引擎换成栅格遮挡体即可复用。

### 5.4 一个必须主动说清的边界

**遮阴 ≠ 降温。** 本项目输出的是物理上定义明确的"在阳光下暴露的分钟数 / 阴影覆盖米数"，不是体感温度、不是 UTCI。做热负荷换算需要平均辐射温度 Tmrt 模型（含长波辐射、风、湿度、衣着、代谢），那是另一个量级的工作。**我们不输出"降温几度"。**

## 6. 低太阳高度角：误差放大的几何推导（含算例）

### 6.1 公式

建筑按**竖直棱柱**处理（同一栋楼顶面等高），阴影长度：

```
L = h / tan(e)                     h：建筑高度，e：太阳高度角
```

误差传递：

```
dL = dh / tan(e) = dh · cot(e)     高度误差被 cot(e) 放大成阴影长度误差
dL / L = dh / h                    相对误差只与高度相对误差有关，与 e 无关
```

**实现（零依赖版 `tools/build.py`）**

- **阴影环**：取「楼轮廓顶点 ∪ 沿太阳反方向平移 `L` 后的轮廓顶点」的**凸包**（Andrew 单调链），一个环代表一栋楼；`L` 上限 500 m；**不做多边形并集**（前端在离屏画布叠加后统一上透明度）。
- **点包含**：**射线法**判断点是否在阴影里，不依赖任何几何库。
- **加速**：一帧的阴影环放进 **25 m 均匀网格索引**，查询时只测同格候选环。网格只影响速度，不影响结果。
- **路线**：无向图 + 手写 **heapq Dijkstra**。最快路线边权 = 边长；阴凉路线边权 = `边长 × (1 + 6.0 × 暴晒比例)`（`COOL_FACTOR = 6.0`，为什么是 6 见 7.5 节）。

**凸包包络的近似在哪（这是唯一可能"多算阴影"的地方，要主动说）**

- 对**凸多边形**建筑（绝大多数）：轮廓 ∪ 平移轮廓的凸包 = 真实扫掠阴影，**精确**。
- 对**凹形**建筑（L 形、U 形、带内院）：凸包会把凹口"填平"，多覆盖一点地面 → 局部**多算阴影** → 那一小块被判成"阴凉"。
- 量级：只在建筑自身轮廓附近（十几米内），且远小于"未计树木"造成的偏差。

### 6.3 算例 1（题目要求的那个数）

一栋 **h = 15 m** 的楼，太阳高度角 **e = 10°**，`tan(10°) ≈ 0.176327`：

```
L(15 m) = 15 / 0.176327 ≈ 85.1 m
若高度实际是 16 m（误差 +1 m）：
L(16 m) = 16 / 0.176327 ≈ 90.7 m
阴影长度差 ≈ 5.7 m
```

**高度角 10° 时，1 m 的高度误差导致约 5.7 m 的阴影边界误差。** 5.7 m 相当于十几个人并排——这种边界对"站阴影里还是太阳下"已经没有意义。

### 6.5 方位角误差的同类换算（二阶项）

阴影沿太阳反方向拉长，方位角误差造成**横向偏移**：`横向偏移 ≈ L · Δθ(弧度)`，`Δθ = 1° ≈ 0.01745 rad`。
算例：h = 15 m、e = 10° → L ≈ 85 m，方位角差 1° → 横向偏约 **1.5 m**。比长度误差小一个量级，不是主项。

### 6.6 由此推出的产品决策（不是拍脑袋）

1. **阈值取 15°**：15° 时 1 m 高度误差 → 3.7 m 阴影误差，已超过一条人行道宽。此时界面显示黄色"低置信度"，文案"此时数据仅作参考"。
   - 本项目实际触发：07:00、07:20、07:40、16:40、17:00 共 5 帧。
   - 注意 **16:40 那一帧也会亮黄条**——而它恰好是全天"少晒"最高的帧（6.2 分钟）。这是好事：数字照给，但明确标注这个数在低置信区。
2. **低于 3° 干脆不画**：`L` 会超过 500 m 截断上限，且 `cot3° ≈ 19`，1 m 误差 → 19 m 阴影误差，任何图形都是噪音。代码里 `el <= 3.0` 直接返回空阴影。
3. **不追求"全时段精确"**：07:00 那帧我们只承诺"两条路差别很小"，不承诺绝对阴影边界。

### 6.7 帧步长（20 分钟）的时间粒度

- 前端查表是"最近帧"，最大时间偏差 **10 分钟**；
- 傍晚太阳高度角每 20 分钟变化约 4~5°（16:20 18.2° → 16:40 14.0°），对应 12 m 的楼，阴影长度从约 37 m 变到约 48 m——**一帧之间边界能移动十几米**；
- 所以"某一帧的阴影边界"应理解为 ±10 分钟的平均状态。20 分钟是"数据量（31 帧 × 285 个多边形 ≈ 0.84 MB）与精度"的折中。

## 7. 阴影覆盖米数：换算口径与全时段表

### 7.1 换算公式（**答辩被问就写这个**）

路线数据里只有 `minutes`（分钟）和 `sun_minutes`（暴晒分钟），阴影覆盖米数由同一个常量反推：

```
暴晒里程 = sun_minutes × 60 × WALK_SPEED
         = sun_minutes × 60 × 1.25
         = sun_minutes × 75        （米）
阴影里程 = length_m − 暴晒里程
阴影覆盖率 = 阴影里程 / length_m
```

`WALK_SPEED = 1.25 m/s` 是 `tools/build.py` 的全局常量，`sun_minutes = 暴晒里程 / 1.25 / 60` 正是生成时的定义，所以这个反推**精确、可复核**。界面用 `js/core.js` 的 `CORE.shadeMeters(route)` 算同一件事。

### 7.5 为什么 `COOL_FACTOR = 6.0`（被问到时别慌）

阴凉路线的权重 `w = 长度 × (1 + 6.0 × 暴晒比例)`。系数就是"1 米暴晒值多少米绕路"：

- **取 4 时**：系统太怕晒，绕路太保守，实测只换来 1~2 分钟的少晒，演示上不好看；
- **取 6**：14:00 稳定给出"多走 44 米 / 少晒 4.0 分钟"、10:00 是"多走 46 米 / 少晒 3.3 分钟"——绕路是肉眼可感知的，但不是离谱的 1 公里；
- **它是手调出来的演示档位，不是标定值**。公平地说：这个系数应该由用户调研或热暴露调查决定，我们只是选了一个讲解时站得住的档位。

### 7.6 界面上的文案精度规则（为什么"多走"用米、"少晒"用小数）

早期版本把"多走"和"少晒"都用整分钟显示，结果 **0.5 分钟被显示成 1 分钟**、3.4 显示成 3 分钟，和实测数字打架。现在的规则是 `js/core.js` 里定死的：

| 少晒 > 0.5 但绕路 < 5 米 | 「几乎不多走（X 米），少晒 Y.Y 分钟。」 | 罕见 |
| 阴凉路线反而更快 | 「阴凉路线反而更快，还少晒 Y.Y 分钟。」 | 罕见 |
| 优势不明显（少晒 ≤ 0.5、多走 > 0.5 分钟） | 「此时段阴凉路线优势不明显（多走 X 分钟，少晒 Y.Y 分钟）。」 | 新数据基本不触发 |
| 两条路几乎一样 | 「两条路线差别很小，走哪条都行。」 | 夏至 12:00 |

### 7.7 采样精度：为什么正午"最快路线阴影覆盖只有 3%"

每条边只用 **4 个采样点**判定晒/不晒，所以**窄阴影带会被漏算**：

- 正午 12:00，12 m 的楼影子只有约 9.4 m 长，路边的窄条经常落在两个采样点之间；
- 于是"最快路线阴影覆盖 3%"这个数**偏小**，真实值更高；
- 正确说法：**"按 4 点采样，正午最快路线几乎没有采到阴影（3%）"**，不要说成"完全没阴影"。

这是"分钟级量化误差"的来源之一，也是为什么我们只承诺相对差异。

### 7.8 现场算路 vs 预计算：同一套算法，长度差 0 米

页面不只有两条写死的路线：`data/graph.js`（**101.2 KB**）把 **474 节点 / 613 边（边长毫米精度）**、**31 帧 × 613 条的暴晒千分比（0–1000）**、**53 个可选中大地名**发给浏览器，`js/router.js`（227 行，二叉堆 + Dijkstra + 吸附）在图里现场求解。

- **吸附**：地图点选吸附上限 **120 米**，且只允许吸附到**最大连通分量的 466 个节点**（孤岛小路吸上去会算出"没有路"）。
- **一致性**：冒烟测试把 **2 对起终点 × 31 帧 = 62 个组合**逐个对拍 JS 现场算 vs Python 预计算，断言 **长度全等（最大差 0 米）、暴晒分钟差 ≤0.05 分钟**。
- **为什么不矛盾**：阴影（几何）是预计算的，路径选择是现场跑的；两者共用同一份 `exposed` 边权，所以"现场算"不是另一套近似。
- **短距离会"没差异"**：怀士堂 → 黑石屋 **298 米**，四个时刻两条路几乎相同（少晒 0.0~0.1 分钟）。阴影规划只对**长距离、且有平行道路**的场景有意义，1113 米横穿校园才有 4.0 分钟空间——这一点我们主动写进边界。

### 7.9 水系的替代来源（无 OSM 依赖）

**结论先行**：页面上的湖（园东湖）**不是 OSM 测绘图元**，而是从路网几何反推的**示意轮廓**（`approx: true`），页面画**半透明填充 + 虚线边**，图例写「水系」。道路与楼名仍然是真实 OSM 数据；**路名仍缺**（`data/raw/roadnames.json` 为空，路上不写字），这条降级没有变。

**为什么不用 OSM 水系**：本次 OSM 全线不通（本机直连超时、代理 502，Overpass 4 个镜像 + 法国站 + OSM 主 API 全部失败），wikidata 也没有园东湖条目——等数据不如换方法。

**算法（`build.py lakering`，可复现，不是手糊多边形）**：

1. 从 `data/raw/ways.json` 建**完整路网**：**1194 节点 / 1373 边**（只取几何，不按通行性裁切）；
2. 用生成森林的非树边枚举**基本环**（每个环 = 一条非树边 + 对应的树上路径）；
3. 过滤：环面积 **4000–80000 m²**、周长 **380–1500 m**、质心在校园内；按**环内建筑占比**从低到高排序（越低越像湖，湖面不会有建筑）；
4. 人工在图上指认：选校园东侧中部、中心 **(536, −85) 米** 的空块；
5. 多边形向内收 **6%**（`--shrink 0.06`，补偿路中线到湖岸的路宽），再做 **2 轮 Chaikin 切角平滑**（`--smooth 2`，可 0–4），得到 **40 顶点 / 16,814 m²（≈1.7 万 m²）**，写入 `data/raw/water.json` 并标 `approx: true`；
6. 再跑 `python tools/build.py basemap` 重新生成 `data/basemap.js`，页面才画上去。

**快速试位置的另一条命令**：`python tools/build.py waterblob --x 300 --y 180 --w 240 --h 150` —— 按米坐标放一块带轻微起伏的椭圆示意水面（48 顶点），同样写 `data/raw/water.json` 并标 `approx`。

页面上的道路与楼名**不是手绘、不是示意图**，而是由 `build.py basemap` 从本地 OSM 数据离线渲染：

| 图层 | 数据 | 数量 | 来源 / 规则 | 当前状态 |
|---|---|---|---|---|
| 道路 `roads` | 折线 `{t,p}`，四档线型 `main` / `local` / `service` / `path` | **296 段** | `data/raw/ways.json` 原始 **297 条 way**，按可视范围 bbox±60 m 裁切后得到 296 段 | ✅ 已绘制 |
| 楼名 `labels`（`k=b`） | `{n,x,y,k,r,a}` | **60 条** | 285 栋里 **68 栋有 name**；过滤 `572`、`532 533`、`东区3180` 等 OSM 编号型 / 流水号型垃圾名；按 `r`（重要度档）→ 底面积 `a` 降序排 | ✅ 已绘制（1400×900 实际画出 50 个，其余被碰撞避让跳过） |
| 湖名 `labels`（`k=w`） | `{n,x,y,k,r,a}` | **1 条** | 与水面同名「园东湖」，`r=1`，`a=16814`；12.5 px 深蓝色，比楼名大一号 | ✅ 已绘制（示意） |
| 水系 `water` | `{n,p,approx}` | **1 处** | `lakering` 环反推 + 内收 6% + 2 轮平滑；`approx: true` | ✅ 已绘制（**示意轮廓**，半透明 + 虚线边） |

**为什么段数是 296 而不是 297**：297 是 `ways.json` 里原始 OSM way 条数；底图按可视范围裁切后，最终得到 296 段折线——所以"**296 段 ≠ 297 条**"，别把段数当 way 数，也别把两者混着写。

**示意不是测绘（必须能说清）**：湖面 = 几何推断 + 人工指认，**位置和量级可信、岸线细节不可信**；所以数据标 `approx: true`、页面画虚线边、图例写「水系」。真实岸线要等网络恢复后 `python tools/build.py water` 抓 `natural=water` 再替换。**不说"园东湖的准确边界"**，只说"约 1.7 万 m² 的示意轮廓（中心 (536, −85) 米）"。

**与算路的关系**：底图与算路都从同一份 `ways.json` 派生——`basemap` 只负责"画"，`routes` 负责"算"（613 边图）。画的路和算的路不是两套数据，所以不会出现"地图上明明有路、算路却说没路"的矛盾；湖不参与算路。
