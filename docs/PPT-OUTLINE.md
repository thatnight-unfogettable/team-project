## P6 · 原理：一条公式 + 31 帧预计算

```
阴影长度  L = 楼高 h / tan(太阳高度角 e)
阴影形状  = 楼轮廓 ∪ 轮廓沿太阳反方向平移 L 后的凸包
是否在阴影里 = 射线法判断
```

- 太阳位置：NOAA 简化算法（本地算，误差约 0.01°）；高度角 52.1°（正午）→ 19 m 楼影 14.8 m。
- 一天 **31 帧** × **285 栋** 楼 → 前端只查表；页面数据约 **1.08 MB（1103.6 KB）**（阴影 861.6 KB）。
- 路线：无向图 + heapq Dijkstra；阴凉权重 `边长 × (1 + 6.0 × 暴晒比例)`。
- 关键：**没有回路就没有"换一条路"**——校园路网 **613 条边 / 474 个节点 / 143 个独立回路**。

**口播**："阴影是几何确定量，所以可以离线算一次、查一辈子。"

## P9 · 为什么可信：四个诚实机制（差异化页）

1. **主动降级**：太阳 < 15° 的 **5 帧**（07:00 / 07:20 / 07:40 / 16:40 / 17:00）亮黄色"低置信度"条，不藏。
2. **可复核的换算**：页面上的"阴影覆盖米数"不是黑盒——`阴影米数 = 长度 − 暴晒分钟 × 60 × 1.25`，一条算式就能复算（14:00：1113 − 14.0×75 = 63 m ≈ 6%）。
3. **现场算 = 预计算**：任意两点在浏览器里跑 Dijkstra，但 **62 个「帧 × 起终点」组合**逐个对拍，与 Python 预计算最大差 **0 米 / ≤0.05 分钟**——不是另一套近似。
4. **测试锁口径**：`node tools/smoke.js` **97 条断言全过**，含 7 条底图断言（结构完整、道路全部来自本地 OSM 路网、四档线型齐全、坐标在可视范围内、楼名在校内、标注数 ≥60、按重要度排序）、6 条校园边界回归（所有建筑质心在校内、所有路线采样点在校内、14:00 两条路线最大偏离 ≤120 m）与 17 条算路断言（含 4 条地图点选）。

**口播**："判断一个数据产品靠不靠谱，看它敢不敢告诉你哪里不准——这四条就是我们的答案。"

## P10 · 边界：我们不承诺什么

- **不承诺"降温几度"**：只输出"暴晒分钟 / 阴影覆盖米数"，不碰体感温度（那要 Tmrt 模型）。
- **不承诺绝对阴影面积**：高度 93% 是 12 m 估算，误差方向**双向**（对高楼偏低→偏晒，对低层偏高→偏凉），净方向不确定。
- **没算树、车、临时棚**：真实阴影只会比图上**多**，所以"偏晒"是保守方向；但树荫很可能才是校园阴凉主力（11 月正午全网阴凉只有 14.7%，这个数低得反常）。
- **4 点采样**：窄阴影带会被漏算，正午最快路线只采到 **3%** 阴影，不能说成"完全没阴影"。
- **短距离常常没差别**：怀士堂 → 黑石屋 **298 米**，四个时刻两条路几乎相同（少晒 0.0~0.1 分钟）；阴影规划只对**长距离 + 有平行道路**的场景有意义——不夸大。
- **结论在主演示起终点上验证**：另外 1 组是学生饭堂 → 老年人活动中心（14:00 多走 57 米、少晒 3.3 分钟）；任意两点是现场算，与预计算 62 组合对拍一致。

**口播**："一个诚实的数据产品，应该能列出自己不成立的场景。"
